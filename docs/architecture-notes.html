From Message-Based Chat to Event-Driven Agent Runtime

How excruciating real-world friction forced a ground-up re-architecture of the data layer. A narrative in 14 chapters.

1 The Original Architecture

The system started as a standard chat application. Messages were the core data model, and streaming callbacks directly mutated chat messages in-place. The mental model was simple: an array of message objects, each with a role and content.

mental model
Message[]

The streaming callbacks mapped AI SDK events directly to message mutations:

  • onTextDelta → append/update assistant message
  • onToolCall → create tool-call message, reset currentId
  • onTextDelta → create new assistant message (because currentId was nulled)

This produced a chat display like:

Assistant message
→ Tool call
→ Assistant continuation

The critical implementation detail was a mutable tracking variable:

typescript
currentId = null;  // forced a new assistant message after each tool call

After a tool call completed, currentId was set to null. On the next onTextDelta, the code saw no currentId and created a fresh message object. This was the first hint that the message model was fighting the streaming reality: the presentation layer's need for "message boundaries" was leaking into the streaming logic.

2 The First Friction

The architecture started feeling awkward as the system grew beyond simple Q&A. Several features pushed against the message model:

  • Tool calls streaming their output live
  • Sub-agents spawning and producing their own output
  • Continuous streaming output that didn't fit message boundaries
  • Multiple concurrent execution flows

The architecture began mixing three distinct concerns inside the same runtime logic:

Execution state
currentId, toolBuffer
UI state
appendLiveEvent, callback threading
Persistence state
persistMessage, assistantMessages[]
These were signals that the abstraction no longer fit the runtime behavior cleanly.

Each of these was a code smell — a sign that the message model was being stretched beyond its natural capacity. The system was trying to represent a continuous, nested, parallel execution as a flat array of discrete objects.

3 The Asymmetry Discovery

The most important realization came from comparing two parts of the system that had been built independently.

Main Assistant — Message-Oriented

The top-level assistant was built around the message model. It stored an array of Message objects and mutated them directly during streaming. The message was the central unit of everything: storage, rendering, and state.

Message[] — stored in SQLite, rendered by React, tracked in streaming callbacks

Sub-Agent System — Already Event-Oriented

The sub-agent system, built later for PR review, used a completely different model. It tracked:

{ fullOutput, outputParts, toolCalls } — incremental streaming state, not discrete messages

The sub-agent system naturally modeled streaming, tool lifecycle, execution flow, and incremental output. It didn't have currentId or toolBuffer hacks because it never tried to force events into messages.

Key Realization: The sub-agent system was architecturally ahead of the main chat. It was already treating execution as an event timeline rather than a sequence of chat bubbles.

4 The Conceptual Breakthrough

The asymmetry forced a fundamental reframing:

Execution events ≠ UI messages

Messages are presentation.
Events are execution reality.

AI systems fundamentally behave like continuous event streams — not static chat bubbles.

A single user request produces a cascade of runtime events: text tokens, tool invocations, tool results, sub-agent spawns, sub-agent outputs, errors, retries. Collapsing all of that into a flat Message[] was a lossy transformation that threw away execution structure.

The insight: the UI wanted messages, but the runtime produced events. These are different shapes. Attempting to make one serve both roles caused the friction.

5 Callback Threading — The Silent Coupling

The original streaming pipeline threaded callbacks through multiple layers:

architecture
agentStream.ts
  → callback passed to streamAgentResponse
    → hook callback (useChatSender.onLiveEvent)
      → React state callback (useChatHistory.appendLiveEvent)
        → setState()

This created several problems:

  • Point-to-point coupling — agentStream was directly wired to a specific consumer
  • Threading through hooks — onLiveEvent was threaded through useChatSender → useChat → useChatScreenState
  • Hard-to-follow ownership — who owned the callback? Who could call it? When?
  • Poor extensibility — adding a new consumer (e.g., debugger) required rewiring the entire chain

The callbacks also created a hidden ordering dependency: the callbacks had to be registered before streaming began, which meant the component tree had to be fully mounted before any message could be sent.

6 The Event Bus Insight

The fix was conceptually simple: decouple the producer from the consumers.

Instead of callbacks: runtime directly calling consumers
The runtime simply emits events. Consumers subscribe independently.
architecture
agentStream.ts
  → bus.emit(event)

Subscribers (independent):
  → persistence  (collects events for batch DB write)
  → React UI     (useSyncExternalStore)
  → debugger     (future: tracing, replay)
  → projections  (future: analytics, export)

The bus pattern removed callback threading entirely. The runtime no longer knew who was listening. Subscribers could be added or removed without changing the streaming pipeline. This was the foundation of everything that followed.

7 Global vs Session-Scoped Bus

Two designs were considered for the bus:

Rejected: Global Singleton Bus

A single global bus for the entire application was appealing in its simplicity but had fundamental problems:

  • Filtering everywhere — every subscriber would need if (event.sessionId !== currentSessionId) return;
  • Session mixing — events from different conversations would interleave on the same bus
  • Accidental listeners — a subscriber from session A might accidentally process session B's events
  • Hidden coupling — global state often leads to implicit dependencies
  • Memory leaks — stale listeners from completed sessions must be manually cleaned up

Chosen: Session-Scoped Bus

Each execution session owns its own bus and event log. This aligns naturally with cancellation, replay, observability, and sub-agent isolation.

class AgentSession { readonly bus; readonly events; }

The session scope means:

  • No filtering — every event on this bus belongs to this session
  • No cross-session contamination
  • Natural garbage collection — drop the session, drop its bus
  • Clean sub-agent model — child sessions with parentEventId

8 Event Log as Source of Truth

A critical distinction emerged early:

Event log = source of truth
Bus = transport

The bus distributes live updates in real-time. The append-only event log stores canonical execution history. These are different concerns with different requirements:

Bus
  • Live distribution
  • Fire-and-forget
  • No ordering guarantees
  • No persistence
Event Log
  • Canonical history
  • Append-only
  • Sequenced and ordered
  • Persisted to SQLite

The event log enables replay, persistence, deterministic rendering, debugging, and projections. The bus enables real-time UI updates and subscriber independence. They work together: emit() appends to the log first, then distributes via the bus.

9 The Projection Layer

Once events were the source of truth, the UI needed a way to render them. The answer: a pure projection function.

typescript
groupEventsForDisplay(events: AgentEvent[]): DisplayBlock[]

This function became the heart of the new architecture. It transforms raw execution events into display-oriented blocks. The projection has four essential properties:

Pure No side effects. Same input always produces the same output.
Deterministic No randomness, no date/time dependence, no mutable state.
Side-effect free Does not mutate events, does not write to DB, does not change any external state.
Order-preserving Event sequence determines block sequence. No reordering.

The projection replaced the old stateful closure bookkeeping (currentId, toolBuffer, assistantMessages[], toolMessagesToPersist[]). Instead of mutating tracking variables, the projection walks the event array and builds the block list from scratch on every call.

This was the key shift: The old code used stateful closures that tracked "where we are" in the stream. The new projection is a pure function that determines block structure entirely from the event sequence. The currentId = null hack was replaced by: "when I see a tool-call-start event, flush the current assistant block and open a new one."

10 Runtime vs Presentation Separation

The old architecture had a subtle but pervasive problem: runtime logic was making presentation decisions.

currentId = null; — This is actually presentation logic leaking into execution code. It says "I want a new message bubble here." But that's a UI concern, not an execution concern.

After the redesign, the separation became clean:

Runtime: emits execution facts only (text-delta, tool-call-start, tool-call-end)
Projection: decides presentation grouping (assistant message boundaries, tool call blocks, sub-agent blocks)

This separation means:

  • The runtime doesn't need to know about message boundaries, React, or rendering
  • The projection can be changed without touching the streaming pipeline
  • Multiple projections can exist (chat view, timeline view, debug view) from the same events
  • The projection can be tested in isolation with fixture event data

11 Transport vs Semantic Events

Another important distinction emerged when thinking about what to store in the event log:

Transport-Level Events (stored)

These are the canonical, persisted runtime events. They remain faithful to actual execution:

text-delta, tool-call-start, tool-call-end

These are "execution facts." text-delta is a provider-level artifact — it records exactly what the AI SDK sent, as it was sent. Different providers may emit different delta patterns, and the log faithfully captures those differences.

Semantic/Derived Events (not stored)

These are synthesized from transport events at projection time:

assistant-message-updated, assistant-message-complete

These are NOT stored in the event log. They are derived by transformers at render time. Storing them would create duplicated truth layers, invalidation problems, and replay inconsistencies.

Rule: Only execution facts go in the event log. Semantic views are derived at projection time, never stored.

12 React State Evolution

The React integration went through two phases:

Phase 1: Array State (rejected)

setLiveEvents(prev => [...prev, event])

This reallocates the entire array on every event. For streaming AI producing hundreds of tokens per second, this causes continuous memory churn and unnecessary re-renders.

Phase 2: External Store via useSyncExternalStore

useSyncExternalStore(session.subscribe, session.getSnapshot)

The session owns the append-only event store. React subscribes to it and reads immutable snapshots. The store only notifies React when the snapshot actually changes (batched notifications consolidate rapid events).

Key details:

  • getSnapshot() returns a cached copy, updated synchronously in emit()
  • Notifications to React are batched via setTimeout(0) — multiple emits in one microtask produce one render
  • The EMPTY_EVENTS constant prevents infinite loops when no session is active (a new [] literal on every call would make React think the store changed every render)
  • Stable references: the subscribe and getSnapshot callbacks must be stable or use refs to avoid re-subscription loops

13 Sub-Agents as Sessions

The sub-agent system originally used custom plumbing: a separate subAgentBus, manual state management, and special-case rendering logic. The deeper realization was:

A sub-agent is not "special." A sub-agent is just another AgentSession with a parent linkage.

In the new model:

AgentSession(parentEventId: string) — child session linked to parent tool call

The child session has its own event log, its own bus, and its own lifecycle. Events can be forwarded to the parent bus via the parentEventId link. This naturally forms a session tree:

tree
Root Session (main chat)
  → Researcher (child session)
  → Debugger (child session)
      → Security Auditor (child of Debugger)
  → Planner (child session)

Each node in this tree is the same AgentSession class, with the same capabilities. No special sub-agent runtime, no custom state management, no manual forwarding.

14 The Final Architecture

AI SDK Runtime
↓
AgentSession
↓
Append-only Event Log
↓
Event Bus (live transport)
↓
Projection Layer
↓
UI  |  Persistence  |  Replay  |  Debugging

The resulting architecture is a pipeline. Each layer has a single responsibility. No layer reaches across another. The event log is canonical storage; the bus is live transport; the projection is the only layer that knows about UI shapes.

The 6 Key Principles

1. Execution events are primary UI messages are derived views. Events are the source of truth. Never let presentation concerns drive execution logic.
2. Event logs are canonical The bus distributes live events. The log stores history. They serve different purposes and should be designed differently.
3. Runtime and presentation must be separated Execution should not decide UI grouping. currentId = null was a violation of this principle.
4. Projections should be pure Deterministic, replayable, side-effect free. Same events → same display, always.
5. Sub-agents are runtime sessions Not special-case tools. Same class, same lifecycle, parent linkage via event ID.
6. AI systems behave like streaming runtimes Not traditional request/response chat apps. Design for continuous, nested, parallel execution from day one.
