Excelsior Architecture Review

A walkthrough of six architectural problems and their solutions — from ambient coupling to explicit ownership.

Introduction

This document walks through the architectural state of Excelsior before and after a focused refactoring effort. Each section identifies a specific problem, shows the problematic code pattern, explains the concrete risks, and then demonstrates the solution with the actual post-plan code.

The six problems addressed are:

Pre-Plan vs Post-Plan Architecture

The core architectural shift is from implicit ambient coupling to explicit layered ownership.

Before: Soft Boundaries

Runtime emits raw events ↓ (direct subscription) UI hooks subscribe directly ↓ (global buses) Contexts coordinate orchestration ↓ (module-level state) Buses are globally observable ┌─────────────┐ │ Runtime │ ← global bus listeners, mutable session store └──────┬──────┘ │ events (unversioned, no causation) ┌──────▼──────┐ │ UI Hooks │ ← orchestration logic mixed with React state └──────┬──────┘ │ mutable refs, module-level arrays ┌──────▼──────┐ │ Contexts │ ← coordination sprawl, thin wrappers └─────────────┘

After: Explicit Layers

1. Event Contract Formalization

Problem Events carried session context but no causal chain or schema version. Replay, debugging, and distributed execution were impossible.
Solution Every event now carries version, causationId, and correlationId. The causal chain is explicit.

Before

src/lib/runtime/events.ts
export interface AgentEvent<T> {
  id: string;
  sessionId: string;
  sequence: number;
  type: T;
  timestamp: string;
  data: AgentEventDataMap[T];
  parentEventId?: string;      // optional — session hierarchy only
  relatedToolCallId?: string;  // optional — tool binding
}

What was missing: no way to determine why an event happened (causation), no stable trace across sessions (correlation), and no schema version for forward-compatible replay.

After

src/lib/runtime/events.ts
export const EVENT_SCHEMA_VERSION = 1;

export interface AgentEvent<T> {
  id: string;
  sessionId: string;
  sequence: number;
  type: T;
  version: number;           // schema version — enables forward-compat replay
  causationId: string;      // event ID that caused this event (causal chain)
  correlationId: string;    // stable ID across a logical operation
  timestamp: string;
  data: AgentEventDataMap[T];
  parentEventId?: string;
  relatedToolCallId?: string;
}

How causation flows

The AgentSession tracks _lastEventId internally. Each emit() call automatically sets causationId to the previous event's ID:

src/lib/runtime/agentSession.ts (emit method)
emit(type, data, overrides?) {
  const event = makeEvent(this.id, type, data, this._seq++, {
    parentEventId: this.parentEventId,
    correlationId: this.correlationId,
    causationId: this._lastEventId ?? undefined,
    ...overrides,
  });
  this._lastEventId = event.id;
  Object.freeze(event);
  this._events.push(event);
  this._snapshot = [...this._events];
  this.bus.emit("event", event);
  this._notify();
}

How correlation propagates across sessions

When a sub-agent is spawned, the child session inherits the parent's correlationId, so all events across the hierarchy trace to the same logical operation:

src/agent/review/spawnSubAgent.ts
// Before: new AgentSession(parentSession.id);
// After:
const childSession = new AgentSession(
  parentSession.id,
  parentSession.correlationId  // inherit correlation across sessions
);
Replay becomes possible With EVENT_SCHEMA_VERSION, a replay engine can check if the stored event schema matches the current reader. If not, it can apply a migration. The causationId chain means replay can reconstruct exact causal ordering.

Pattern: Before (hub observers)

src/lib/runtime/bus.ts
// Module-level global — every channel bus forwarded to this set
const _hubListeners = new Set<HubObserver>();

export function observeHub(observer: HubObserver): Unsubscribe {
  _hubListeners.add(observer);
  return () => { _hubListeners.delete(observer); };
}

export function createChannelBus<T>(channel: string): Bus<T> {
  const inner = createBus<T>();
  const origEmit = inner.emit.bind(inner);
  inner.emit = ((event, data) => {
    // Every single emit forwarded to ALL global listeners
    for (const listener of _hubListeners) {
      try { listener({ channel, event, data }); } catch {}
    }
    origEmit(event, data);
  }) as Bus<T>["emit"];
  return inner;
}

Any module importing createChannelBus silently leaked events to every hub observer. No way to scope observation to a specific session or component tree.

Pattern: After (scoped hub)

src/lib/runtime/bus.ts
// Hub is now an explicit interface + factory — scoped per owner
export interface Hub {
  observe(observer: HubObserver): Unsubscribe;
  notify(channel: string, event: string, data: unknown): void;
  dispose(): void;                // ← deterministic cleanup
}

export function createHub(): Hub {
  const listeners = new Set<HubObserver>();
  return {
    observe(observer) {
      listeners.add(observer);
      return () => { listeners.delete(observer); };
    },
    notify(channel, event, data) { ... },
    dispose() { listeners.clear(); },  // ← eliminates all observers
  };
}

// createChannelBus now optionally accepts a hub — no hub = no global forwarding
export function createChannelBus<T>(
  channel: string,
  hub?: Hub,              // ← optional, scoped
): Bus<T> {
  ...
}

Pattern: Before (sub-agent store)

src/tui/hooks/useChatHistory.ts
// Module-level reactive counter — shared across all hook instances
let _subAgentVersion = 0;
const _subAgentListeners = new Set<() => void>();
subAgentBus.on("spawned", triggerSubAgentUpdate);
subAgentBus.on("output", triggerSubAgentUpdate);
subAgentBus.on("done", triggerSubAgentUpdate);

  subscribe: (cb) => { _subAgentListeners.add(cb); return () => _subAgentListeners.delete(cb); },

If useChatHistory ever mounted twice (React Strict Mode, hot reload), listeners would accumulate and never clean up because the bus subscriptions were permanent.

Pattern: After (scoped store)

src/tui/hooks/useChatHistory.ts
// Scoped per hook instance — subscriptions are disposable
class SubAgentProjectionStore {
  private _version = 0;
  private _listeners = new Set<() => void>();
  private _unsubs: Array<() => void> = [];

  constructor() {
    // Bus subscriptions are tracked for cleanup
    this._unsubs.push(subAgentBus.on("spawned", () => this._triggerUpdate()));
    this._unsubs.push(subAgentBus.on("output", () => this._triggerUpdate()));
    this._unsubs.push(subAgentBus.on("done", () => this._triggerUpdate()));
  }

  subscribe(cb) { ... }

  dispose() {                      // ← fully cleans up
    for (const unsub of this._unsubs) unsub();
    this._unsubs = [];
    this._listeners.clear();
  }
}
Key insight: ownership trees Instead of "global listeners", every subscription now belongs to a scope. When the scope disposes (session ends, component unmounts, plugin unloads), all subscriptions, timers, and controllers are cleaned up deterministically. This is the prerequisite for plugins, hot reload, and concurrent sessions.

3. Stateful Orchestrator → Stateless + RunHandle

Problem SessionOrchestrator stored private currentSession, meaning one orchestrator instance could only manage one run at a time. Cancel was a method on the orchestrator, not the run.
Solution Orchestrator became stateless. startRun() returns a RunHandle that owns the lifecycle. Multiple runs can coexist. Cancel is on the handle.

Before

src/lib/runtime/sessionOrchestrator.ts
export class SessionOrchestrator {
  private currentSession: AgentSession | null = null;  // ← implicit singleton assumption

  startRun(session, config) {
    this.currentSession = session;     // overwrites any previous run
    const unsub = session.bus.on("event", ...);
    const onComplete = streamAgentResponse(...)
      .then(() => { unsub(); this.currentSession = null; return events; })
      .catch((err) => { unsub(); this.currentSession = null; ... });
    return { events, onComplete };
  }

  cancel() {                          // ← cancel is on the orchestrator, not the run
    this.currentSession?.cancel();
    this.currentSession = null;
  }
}

Problems:

  • Starting a second run while one is in progress silently overwrites currentSession — the first run becomes an orphan
  • cancel() cancels whatever happens to be "current" — no way to cancel a specific run
  • Nested sub-agents can't use the same orchestrator pattern
  • No way to detach a background task while starting a new foreground one

After

src/lib/runtime/sessionOrchestrator.ts
// RunHandle — explicit lifecycle for a single run
export interface RunHandle {
  cancel(): void;                       // cancel is ON the run
  readonly done: Promise<AnyAgentEvent[]>;  // completion promise
}

export class SessionOrchestrator {
  // No instance state at all — pure factory method

  startRun(session, config): RunHandle {
    let unsub = session.bus.on("event", ...);

    const done = streamAgentResponse(...)
      .then(() => { unsub?.(); unsub = null; return allEvents; })
      .catch((err) => { unsub?.(); unsub = null; ... });

    return {
      cancel() {
        session.cancel();       // cancels the session (abort + cleanup)
        unsub?.();              // unsubscribes from bus
        unsub = null;
      },
      done,                     // resolves with collected events
    };
  }
}

Consumers now store a RunHandle ref instead of an orchestrator ref:

src/tui/hooks/useChatSender.ts
// Before:
const orchestratorRef = useRef<SessionOrchestrator>(new SessionOrchestrator());
const cancel = () => orchestratorRef.current?.cancel();

// After:
const runHandleRef = useRef<RunHandle | null>(null);
const cancel = () => runHandleRef.current?.cancel();
Why this matters With a RunHandle, you can:
  • Run multiple orchestrations concurrently (just keep multiple handles)
  • Nest runs (sub-agent orchestrator creates its own handle)
  • Detach background tasks (don't store the handle — let it run free)
  • Replay (create a handle that replays events without executing tools)
  • Implement timeouts per-run (add a timeout timer inside the handle)

After: Service + Thin Hook

src/application/chatService.ts
export class ChatService {
  private orchestrator = new SessionOrchestrator();

  startRun(content: string, options?: {
    history?: AIHistoryRef;
    onComplete?: (events) => void;
  }): ChatRunResult {
    const session = new AgentSession();
    const childSessions = new Map();
    const aiMessages = this.buildMessages(content, options?.history);

    session.emit("user-input", { content });
    persistSession({ id: session.id, ... });

    const ctx = createToolContext({ confirmBus });    // ← capability context

    const handle = this.orchestrator.startRun(session, {
      messages: aiMessages,
      createAgent: () => createAgent(undefined, {
        spawnSubAgent: createSpawnSubAgentTool(session, childSessions),
      }, ctx),
    });

    handle.done.then((events) => {
      persistEvents(events);
      options?.onComplete?.(events);
    });

    return { session, childSessions, handle };
  }
}

5. Projection Ambiguity → Typed ReadModels

Problem Projections existed as standalone functions with implicit contracts. No shared interface meant new projections couldn't reuse the fold pattern.
Solution Created ReadModel<TState, TEvent> interface with initialState() and apply(). Existing projections now expose typed instances.

Before: Implicit contract

src/lib/projection/projectEvents.ts
// Three projection functions, each with its own calling convention:

  events: readonly AnyAgentEvent[],
  options?: ProjectOptions,
): DisplayBlock[] { ... }

export function projectChildEventsToSubAgentState(
  childEvents: readonly AnyAgentEvent[],
  status: "running" | "done" | "error",

export function projectEventsToAIHistory(
  events: readonly AnyAgentEvent[],
): AIHistoryMessage[] { ... }

Each function has a different signature. A new developer faces three different calling conventions. No composability — each projection is standalone.

After: Typed ReadModel

src/lib/projection/readModel.ts
export interface ReadModel<TState, in TEvent> {
  initialState(): TState;              // initial (empty) state
  apply(state: TState, event: TEvent): TState;  // single-event reducer
}

// Generic fold — works with ANY ReadModel
export function projectEvents<TState, TEvent>(
  model: ReadModel<TState, TEvent>,
  events: readonly TEvent[],
): TState {
  let state = model.initialState();
  for (const event of events) {
    state = model.apply(state, event);
  }
  return state;
}
src/lib/projection/projectEvents.ts

6. Tool Dependency Leaks → Capability-Based Context

Problem Tools accessed global services directly. runCommand, write, and edit each imported ConfirmBus and manually managed the request/response lifecycle with randomUUID and promise construction.
Solution ToolContext encapsulates all tool-facing dependencies. Tools check capability gates before acting. The context is created once at the service layer and passed down.

Before: Each tool wired itself to global services

src/agent/tools/runCommand/runCommand.ts (before)
export function createRunCommandTool(confirmBus?: ConfirmBus) {
  return tool({
    execute: async ({ command, args }) => {
      // Manual confirmation protocol — 15 lines per tool
      if (confirmBus && confirmBus.getListenerCount("request") > 0) {
        const callId = randomUUID();                    // ← manual ID
        const approved = await new Promise<boolean>((resolve) => {
          const unsub = confirmBus.on("response", (resp) => {
            if (resp.callId === callId) { unsub(); resolve(resp.approved); }
          });
          confirmBus.emit("request", { callId, toolName: "runCommand", args });
        });
        if (!approved) return "Denied by user.";
      }
      // Actual execution...
    },
  });
}

Every tool that needs confirmation duplicates the same pattern (~15 lines). Tools import randomUUID, ConfirmBus, and Promise. No way to mock or sandbox without mocking ConfirmBus at the module level.

After: ToolContext with capability gates

src/lib/tool/context.ts
export type ToolCapability =
  | "fs:read" | "fs:write" | "shell"
  | "network" | "git" | "sub-agent";

export interface ToolContext {
  capabilities: ReadonlySet<ToolCapability>;  // ← what this tool MAY access
  confirm?: ConfirmCapability;               // ← only present if capability granted
  abortSignal?: AbortSignal;
}

export interface ConfirmCapability {
  getListenerCount(): number;
  request(toolName: string, args: string): Promise<boolean>;
}

// Factory — creates context with appropriate capabilities
export function createToolContext(options?: {
  abortSignal?: AbortSignal;
  confirmBus?: ConfirmBus;
}): ToolContext {
  const capabilities = new Set<ToolCapability>();
  capabilities.add("fs:read");
  capabilities.add("shell");

  if (options?.confirmBus) {
    capabilities.add("fs:write");     // ← write tools only allowed if confirm bus present
    ctx.confirm = {
      request: (toolName, args) => new Promise((resolve) => {
        const callId = randomUUID();
        const unsub = options.confirmBus!.on("response", (resp) => {
          if (resp.callId === callId) { unsub(); resolve(resp.approved); }
        });
        options.confirmBus!.emit("request", { callId, toolName, args });
      }),
    };
  }
  return ctx;
}

Benefits of the context pattern:
  • Sandboxing: A tool can check ctx.capabilities.has("fs:write") before attempting a write. A restricted agent simply doesn't get the capability.
  • Testing: Inject a mock context: 
    const mockCtx = { capabilities: new Set(["fs:read"]), confirm: { request: async () => true, getListenerCount: () => 1 } };
const tool = createRunCommandTool(mockCtx);
  • Remote execution: The context could serialize the request function to send confirmation prompts over a WebSocket instead of a local bus.
  • Plugin isolation: Each plugin gets its own context with a restricted capability set. A "read-only reviewer" plugin gets fs:read and git but not fs:write or shell.

export class AgentManager {
  private _service = new ChatService();
  private _listeners = new Set<() => void>();
  private _session: AgentSession | null = null;
  private _childSessions = new Map<string, AgentSession>();

  getSnapshot(): AgentState {
    return {
      displayBlocks: this._computeDisplayBlocks(),
      isLoading: this._isLoading,
      hasMore: this._loadedCount < this._totalCount,
    };
  }

  subscribe(cb: () => void): () => void { ... }

  send(content: string): void {
    if (this._isLoading) return;
    const result = this._service.startRun(content, { ... });
    this._session = result.session;
    this._childSessions = result.childSessions;
    result.session.subscribe(() => {
      this._liveEvents = session.getSnapshot();
      this._notify();
    });
    result.handle.done.then(() => {
      this._isLoading = false; this._notify();
    });
  }

  cancel(): void { ... }
  loadMore(): void { ... }
  clear(): void { ... }
  dispose(): void { ... }

  private _computeDisplayBlocks(): DisplayBlock[] {
    return groupEventsForDisplay(this._mergeEvents(), {
      getChildEvents: (id) =>
        this._childSessions.get(id)?.getSnapshot() ?? [],
    });
  }
}
src/features/session/useAgentManager.ts
export function useAgentManager() {
  const ref = useRef<AgentManager>(new AgentManager());

  useEffect(() => () => ref.current?.dispose(), []);

  const state = useSyncExternalStore(
    useCallback(cb => ref.current!.subscribe(cb), []),
    useCallback(() => ref.current!.getSnapshot(), []),
  );

  return {
    state,
    send: useCallback(c => ref.current?.send(c), []),
    cancel: useCallback(() => ref.current?.cancel(), []),
    loadMore: useCallback(() => ref.current?.loadMore(), []),
    clear: useCallback(() => ref.current?.clear(), []),
  };
}
