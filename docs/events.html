Event-Stream Architecture

The core insight: AI execution is a continuous event stream, not discrete chat bubbles. The architecture makes events explicit, session-scoped, and the single source of truth.

1. Core Concept: AgentSession

Every agent execution is encapsulated in an AgentSession—a self-contained runtime that owns its event bus (transport) and append-only event log (source of truth). The class exposes three concerns independently: bus for live distribution, log for replay/projection, and snapshot for React integration.

typescript
class AgentSession {
  readonly id: string;
  readonly bus = createBus<{ event: AgentEvent }>();  // transport only
  readonly parentEventId?: string;
  abortController?: AbortController;

  constructor(parentEventId?: string)

  emit(type, data, overrides?): AgentEvent     // appends + snapshots + bus notifies
  cancel(): void                                // aborts + clears pending
  flushNotify(): void                           // force immediate React notification

  getSnapshot(): readonly AgentEvent[]          // cached copy, stable between emits
  subscribe(cb): () => void                     // for useSyncExternalStore
}
ℹ

Bus vs Log: The bus distributes events. The log stores them. Subscribers use the bus for live updates. Replay, persistence, and projections read from the log. This separation means the bus can be synchronous (emit fires immediately) while notifications to React can be batched via setTimeout(0).

2. Event Vocabulary

Events are the atoms of execution. Each represents a single, immutable fact. Events are never mutated—Object.freeze(event) enforces this at runtime.

3. sendMessage() Data Flow

The critical architectural change: sendMessage() is synchronous. It returns the session immediately. The caller attaches React subscribers before any async streaming begins.

1

Create Session

new AgentSession() → bus and internal event log are created. No I/O, no async work.

2

Attach Subscribers

session.bus.on("event", collector) → collects all events for batch persistence at session-end. The bus subscriber runs synchronously for every emit—no batching on the bus, only on React notifications.

3

Emit User Input

session.emit("user-input", { content }) → appended to log, bus distributes, snapshot updated. Persisted to DB immediately (not batched).

4

Return Session

return session → callers (React via attachSession) subscribe to the session via useSyncExternalStore. From this point forward, all events flow to React.

5

Fire-and-Forget Streaming

streamAgentResponse(agent, messages, session, signal) → runs asynchronously. Each AI SDK stream part becomes a session.emit() call. The Promise is not awaited by the caller; it completes in the background.

6

Batch Persist on Completion

.then(() ⇒ persistEvents(allEvents)) → single bulk write at session-end. No per-event DB writes during streaming. Events include text-deltas (needed by projection for assistant text).

4. Projection: Events to DisplayBlocks

The UI never reads raw events. A pure function groupEventsForDisplay() projects the event sequence into DisplayBlock[] for rendering.

The projection is a pure, deterministic, side-effect-free function. Same events → same display blocks, always. This invariant enables replay, snapshot testing, and time-travel debugging.

How grouping works: Consecutive text-delta events coalesce into one assistant block. When tool-call-start interrupts, the assistant block is flushed and a new tool-call block begins. When tool-call-end arrives, the tool block is finalized via flushTool(). This replaces the old currentId = null hack entirely.

5. Terminal Rendering Strategy

Ink renders output to the terminal buffer. To prevent scroll jank when new events arrive, the UI uses a frozen + live tail strategy via Ink’s <Static> component.

Terminal emulators naturally scroll to show new output. Without <Static>, every re-render rewrites the entire chat buffer, resetting the viewport. With <Static>, frozen blocks are never re-touched—only the last 3 blocks update dynamically. The terminal only scrolls for actual new content, not for cosmetic re-renders.

6. React Integration Pattern

typescript
// useChatHistory.ts — stable ref pattern for useSyncExternalStore
const EMPTY_EVENTS: readonly AgentEvent[] = [];

const [activeSession, setActiveSession] = useState<AgentSession | null>(null);

const liveEvents = useSyncExternalStore(
  useCallback(
    (cb: () => void) => {
      if (!activeSession) return () => {};
      return activeSession.subscribe(cb);
    },
    [activeSession],
  ),
  useCallback(() => {
    if (!activeSession) return EMPTY_EVENTS;   // stable reference!
    return activeSession.getSnapshot();
  }, [activeSession]),
);

// Deduplicate events across session boundaries
const displayEvents = useMemo(() => {
  const liveIds = new Set(liveEvents.map(e => e.id));
  const filtered = persistedEvents.filter(e => !liveIds.has(e.id));
  return [...filtered, ...liveEvents];
}, [persistedEvents, liveEvents]);

// Project
const displayBlocks = useMemo(
  () => groupEventsForDisplay(displayEvents),
  [displayEvents],
);
Critical detail: The EMPTY_EVENTS constant prevents an infinite re-render loop. If getSnapshot() returned a new [] literal on every call, useSyncExternalStore would see a "change" every render and loop. A stable reference fixes this.

7. Session Tree: Main + Sub-Agents

Sub-agents are not "special." A sub-agent is just another AgentSession with parentEventId linking it to the spawning tool call. Its events optionally forward to the parent’s bus.

The projectEvents.ts projection handles this naturally: spawnSubAgent tool-call events create a pending tool block. When sub-agent events arrive (via forwarded bus events with matching parentEventId), the projection emits a sub-agent DisplayBlock instead of a tool-call block. No string-matching on tool names anywhere in the rendering pipeline.

8. Architectural Principles

1. Events are immutable facts. Once created, an event is never mutated. Object.freeze(event) enforces this at runtime. No subscriber can tamper with history.
2. Bus is transport, not state. The bus distributes events. The event log is the source of truth. Never read state from the bus—always from the log.
3. Session-scoped isolation. Each execution gets its own bus. No global event bus, no session-ID filtering, no cross-session leaks.
4. Projections are pure. groupEventsForDisplay(events) must be deterministic—same input, same output. No side effects, no mutable state, no date/time dependencies.
5. Store facts, derive views. Only execution facts go in the event log. Semantic views (assistant-message-complete, etc.) are derived at projection time, not stored.
6. Explicit lifecycle. Create → subscribe → start. Never auto-start in a constructor. Separation of creation and execution enables middleware, debugging, and replay.
7. Batch at the boundary. React notifications are batched (setTimeout 0) to coalesce rapid streams of events into a single render. DB writes are batched at session-end. The event bus itself is never batched—subscribers get every event synchronously.

9. Before vs After: Callback Elimination

Old: Callback Threading

// agentStream.ts — accepts callback
streamAgentResponse(agent, messages,
  (event) => onLiveEvent(event)
);

// useChatSender.ts — receives callback
function useChatSender(onLiveEvent) { ... }

// useChat.ts — threads callback
const { appendLiveEvent } = useChatHistory();
const { sendMessage } = useChatSender(appendLiveEvent);
//                      callback coupling ^

Point-to-point coupling. Hooks can't be independently composed. Adding a new subscriber requires rewiring parent components.

New: Session Bus + useSyncExternalStore

// useChatSender.ts — returns session
const session = new AgentSession();

// Persistence subscribes independently:
session.bus.on("event", collectForPersist);

// React subscribes independently:
const liveEvents = useSyncExternalStore(
  (cb) => session.subscribe(cb),
  () => session.getSnapshot(),
);

// No threading needed.
return session;

Bus-based distribution. Hooks are independent. Add subscribers without changing any existing code. React, persistence, and debugger are peers.
