Data Flow

The application is built around an event-driven pipeline: user input → agent execution → event streaming → projection → UI rendering.

Chat Message Flow

User types message
  │
  ▼
useChatScreenState.handleSubmit()
  │
  ▼
useChatSender.sendMessage(content)
  │
  ├── Creates AgentSession (event emitter)
  ├── Emits "user-input" event
  ├── Persists session metadata to SQLite
  └── Starts sessionOrchestrator.startRun()
        │
        ▼
      agentStream.streamAgentResponse()
        │
        ├── Calls agent.stream({ messages })
        │     │
        │     ▼
        │   withRetry() — retries on 429/5xx/network errors
        │     │
        │     ▼
        │   Iterates fullStream async iterable
        │
        ├── For each stream part emits typed events:
        │   "text-delta"    → session.emit("text-delta", { delta })
        │   "tool-call"     → session.emit("tool-call-start", ...)
        │   "tool-result"   → session.emit("tool-call-end", ...)
        │
        └── On completion: persistEvents(), update AI history
              │
              ▼
            useChatHistory receives events via useSyncExternalStore
              │
              ▼
            groupEventsForDisplay() → DisplayBlock[]
              │
              ▼
            ChatHistory renders blocks
              ├── Frozen blocks → <Static> (never re-rendered)
              └── Live blocks → normal React render (streaming updates)

Event Pipeline Architecture

The core insight: every interaction is recorded as an immutable ordered event. Events are:

  1. Emitted by AgentSession.emit() during agent runs
  2. Persisted to SQLite via eventPersistence.ts (with in-memory write-through cache)
  3. Projected into UI display blocks via groupEventsForDisplay()
  4. Replayed into AI conversation history via projectEventsToAIHistory() for memory continuity
agentStream.ts
  │
  │  (1) Raw AI stream parts
  ▼
AgentSession.emit()
  │
  ├── (2) Session event bus → useSyncExternalStore → React re-render
  │
  ├── (3) sessionOrchestrator.onEvent callback
  │
  ▼
eventPersistence.ts
  │
  ├── SQLite (WAL mode)
  └── In-memory LRU cache
        │
        ▼
  useChatHistory → loadSessionEvents() (cache-first)
        │
        ▼
  groupEventsForDisplay()
        │
        ├── DisplayBlock[] → ChatHistory (UI)
        └── projectEventsToAIHistory() → AI memory context

Tool Confirmation Flow

Write/edit/runCommand tools require user approval before execution. This is coordinated through a confirmation bus:

Agent calls write/edit/runCommand tool
  │
  ▼
Tool checks confirmBus.getListenerCount("request") > 0
  │
  ▼
Tool emits confirmBus.emit("request", { callId, toolName, args })
  │
  ▼
useToolConfirmation hook receives request
  │  Sets pending state → ChatScreen shows confirmation Panel
  │
  User presses Y / A / N
  │
  ▼
confirmBus.emit("response", { callId, approved })
  │
  ▼
Tool receives response via confirmBus.once("response")
  ├── approved=true  → executes action
  └── approved=false → returns "Denied by user."
Auto-approve mode: The "approve all" flow sets a session-level flag that auto-approves all subsequent requests for the duration of the session.

PR Review Flow

The review system uses a parallel fan-out with merge pattern:

User opens review screen or types /review
  │
  ▼
usePullRequests fetches PR list via Octokit
  │
  ▼
User selects PR → usePRDiff fetches diff
  │
  ▼
User presses Enter → useReviewOrchestrator.startReview()
  │
  ▼
Creates main agent with reviewOrchestratorPrompt
  + gitDiff tool + spawnSubAgent tool
  │
  ▼
Feeds diff as user message
  │
  ▼
Orchestrator agent analyzes diff
  │
  ├── Spawns Bug Hunter (logic errors)
  ├── Spawns Security Auditor (auth/crypto/dependencies)
  ├── Spawns Code Style Reviewer (style/consistency)
  └── Spawns Infrastructure Reviewer (CI/infra changes)
        │
        ▼
  Each sub-agent runs independently via createAgent()
  │  Events broadcast to subAgentBus
  │  useSubAgentListener updates SubAgentContext
  │  TUI shows SubAgentRow / SubAgentDetail per agent
  │
  ▼
  Orchestrator collects all results
    ├── Deduplicates overlapping issues
    ├── Ranks by severity: CRITICAL > HIGH > MEDIUM > LOW
    ├── Removes false positives
    └── Generates markdown PR comment

Static + Live Rendering

To optimize Ink rendering performance, display blocks are split into two categories:

CategoryCriteriaRendering
Frozenblock.isFrozen === true (terminal status)<Static> — never re-rendered by Ink
Liveblock.isFrozen is undefined (still streaming)Normal React render — re-renders on each delta

Blocks are frozen per-block rather than using a positional heuristic. A block becomes frozen when:

  • An assistant text block is flushed (next event arrives)
  • A tool-call completes (tool-call-end event)
  • A sub-agent reaches "done" or "error" status
  • A user message is emitted
