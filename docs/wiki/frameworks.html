Architecture study guide

Why Excelsior now has mini frameworks

The refactor split two repeated architectural patterns out of agent-host: deterministic event projection and cancellable eventful runs. The goal was not to make Excelsior abstract for its own sake. The goal was to give developers a map: generic mechanics live in small packages, while product decisions stay in agent-host.

What changed

Two private packages were added: @excelsior/projection and @excelsior/run-runtime.

Why it changed

Generic mechanics were hidden inside product files, which made the architecture harder to read and reuse.

How it changed

Agent-host kept domain behavior and now consumes small framework APIs through adapters and read models.

What stayed stable

Commands, persisted events, session behavior, projections, TUI display, and tests remain behavior-compatible.

The Core Idea

A mini framework is useful here only when it captures a stable verb in the system. Projection has the verb fold ordered events into state. Run runtime has the verb manage a cancellable event source. Those verbs are stable. DeepSeek, Ink screens, slash commands, file tools, and persistence policy are product details, so they stay outside the mini frameworks.

The test for a good extraction is simple: the new package should make the code easier to explain without forcing product-specific concepts into a generic layer. If a package needs to know about React, Ink, the AI SDK, GitHub, SQLite, Plan/Act mode, or sub-agent UI rows, it is no longer a generic mini framework.

Before And After

Package Responsibilities

@excelsior/core

Serializable contracts shared by host and TUI: sessions, workspace, display blocks, command results, mode, confirmations, and panel ids.

@excelsior/projection

Generic read-model fold. It knows nothing about Excelsior events, UI blocks, AI messages, files, persistence, or React.

@excelsior/run-runtime

Generic eventful run lifecycle. It owns event envelopes, sequence numbers, causation, correlation, snapshots, subscriptions, cancellation, and orchestration hooks.

@excelsior/agent-host

Product backend. It defines Excelsior event names, adapts AI SDK streams into events, owns tools, sessions, persistence, commands, sub-agents, and the public host facade.

@excelsior/tui

Ink frontend. It consumes the host facade and renders projected state. It should not parse raw model streams or read persistence directly.

Projection Framework Deep Dive

Projection was the smaller and safer extraction. The code already had a generic shape: start with initial state, apply each event, return final state. The refactor moved that shape into @excelsior/projection and kept the product read models in agent-host. 

export interface ReadModel<TState, TEvent, TContext = undefined> {
  initialState(): TState;
  apply(state: TState, event: TEvent, context?: TContext): TState;
}

export function projectEvents<TState, TEvent, TContext = undefined>(
  model: ReadModel<TState, TEvent, TContext>,
  events: readonly TEvent[],
  context?: TContext,
): TState;
Before

readModel.ts lived inside agent-host next to product projection code, so generic mechanics and Excelsior-specific behavior looked like one thing.

After

@excelsior/projection owns the fold. Agent-host owns chatTranscriptProjection, aiHistoryProjection, and subAgentProjection.

Why

Reading the code now tells you which parts are reusable mechanics and which parts are product interpretation of runtime events.

How

Display projection calls projectEvents(CHAT_TRANSCRIPT_MODEL, events, context), then finalizes pending assistant/tool state for the live UI.

Run Runtime Framework Deep Dive

The runtime extraction was broader but followed the same rule. The framework owns the lifecycle of an eventful run, not the meaning of an Excelsior agent. Agent-host still decides what a text-delta means, how to stream from the AI SDK, when to record events, and how tool context works. 

const run = new EventfulRun<AgentEventDataMap>({
  idPrefix: "run",
  sessionId,
  parentEventId,
  correlationId,
  parentSignal,
  eventVersion: 1,
  terminalEventTypes: [RUN_END],
});

const handle = orchestrator.start(run, {
  execute: async ({ signal }) => {
    await streamAgentResponse(agent, messages, run, signal);
  },
  shouldRecordEvent: (event) => event.type !== RUN_START,
  recordEvent: (event) => recorder.recordEvent(sessionId, event),
});
Before

AgentRun owned generic run mechanics and Excelsior event typing. RunOrchestrator knew about messages, AI agent creation, stream execution, and recorder behavior.

After

EventfulRun owns generic lifecycle. AgentRun is a typed adapter. RunOrchestrator accepts execution and recorder callbacks instead of importing host concepts.

Why

The cancellation/event/subscription lifecycle is useful beyond this exact AI stream. Keeping it generic makes it easier to test and easier to reason about.

How

createRunSession is now the adapter boundary. It creates the typed run, tool context, recorder callbacks, and AI stream execution function.

Decision Principles

Extract mechanics, not product behavior

Projection and run lifecycle are mechanics. Model streaming, Plan/Act mode, confirmations, sessions, and sub-agent UI are product behavior.

Preserve public adapters during migration

AgentRun kept its existing import path so agent-host code and tests did not need a risky large-bang rewrite.

Keep persisted event schema stable

The event envelope still has the same fields: id, runId, sequence, type, version, causationId, correlationId, timestamp, data, parentEventId, and relatedToolCallId.

Test both framework and product usage

Framework tests prove generic behavior. Existing agent-host tests prove the adapter still preserves Excelsior behavior.

What To Study First

  1. Read packages/projection/src/index.ts. It is tiny on purpose. Understand the fold.
  2. Read chatTranscriptProjection.ts. Notice how product behavior sits on top of the generic fold.
  3. Read packages/run-runtime/src/eventfulRun.ts. Follow id creation, sequence, causation, snapshot, bus emission, and cancellation.
  4. Read packages/agent-host/src/lib/runtime/agentRun.ts. It should feel almost boring because it is now just the typed adapter.
  5. Read createRunSession. This is where agent-host adapts tools, stream execution, recorder behavior, and mode into the generic runtime.
  6. Read projectionFramework.test.ts and runRuntimeFramework.test.ts. They explain the framework contracts better than comments would.

How To Extend Safely

Adding a new projection

Create a product read model in agent-host. Use @excelsior/projection only for the generic fold. Keep side effects out of the projection.

Adding runtime behavior

If it is about event envelopes, cancellation, subscriptions, or orchestration callbacks, it may belong in run-runtime. If it mentions AI, tools, sessions, or persistence schema, it belongs in agent-host.

Adding an event type

Add it to agent-host's event data map and event name constants. The generic runtime should not know the new event's meaning.

Changing persistence

Change recorder or event store code in agent-host. The generic runtime should only call the callback it is given.

The practical payoff is not just reuse. It is cognitive compression. When a developer asks "where does this belong?", the answer is now more obvious: generic folds go to projection, generic run lifecycle goes to run-runtime, and Excelsior-specific behavior stays in agent-host.
