Architecture

Layered, event-driven, feature-owned

The codebase is organized around a small number of hard boundaries. React/Ink renders state. `AgentManager` owns UI-facing state. `ChatService` and `createRunSession` wire model runs. Runtime objects produce events. Persistence records events and metadata. Projection code translates events into chat blocks and model history. Tool execution is gated by a run-scoped `ToolContext` that carries mode, confirmation, cancellation, and workspace bounds.

Responsibility Chart

State ownership

AgentManager is the UI-facing store. It exposes a snapshot through useSyncExternalStore via useAgentManager, and everything in the TUI reads from that snapshot, including current Plan/Act mode.

High ownership concentration by design: one observable store reduces accidental React state forks.

Persistence ownership

RunRecorder owns event append, checkpoint append, raw loading, completed loading, and deletion. SQLite helpers own metadata tables only.

Events and metadata are separate because they have different write patterns.

Primary Boundaries

Boundary Code What crosses it What should not cross it
TUI to application useAgentManager, useChatScreenState Send, cancel, switch session, snapshots. Raw event mutation or direct persistence calls, except command-specific reset helpers.
Application to runtime ChatService.submitUserTurn, createRunSession Messages, session id, recorder, sub-agent sink, mode, tool context. React UI concerns or Ink components.
Runtime to persistence RunOrchestrator, RunRecorder Append-only runtime events and turn checkpoints. Rendered chat blocks or model history projections.
Events to display projectionMerger, projectEvents Immutable event arrays in, projected blocks out. Side effects, file writes, network requests.
Features to app shell CommandRegistry Command definitions and panel definitions, including app features such as `/mode`. Global switch statements for every command.
Tools to user approval ToolContext.confirm, confirmBus Structured confirmation metadata: tool name, args, file path, action, and optional unified diff. Direct file mutation without mode checks and confirmation.

Why Event-Driven?

Agent runs are not a single response string. They include user input, streamed text chunks, tool-call starts, tool-call results, sub-agent attachment events, errors, cancellation, and completion checkpoints. Representing that as an ordered event stream allows the same data to serve four jobs: live UI, persisted restore, future model context, and debugging.

The most important architectural invariant is that projections are deterministic. If you replay the same completed event sequence, you should get the same chat blocks and AI history. This is why projection code is kept under packages/agent-host/src/lib/projection and does not reach into React or persistence.

Architectural Tradeoffs

Chosen: JSONL events plus SQLite metadata

Streaming events are frequent and append-only, which fits JSONL. Session titles, workspaces, settings, and error logs are relational metadata, which fits SQLite.

Chosen: feature-owned commands

Commands and panels live next to feature-specific helpers. This avoids one central command file growing into a mixed-purpose controller.

Chosen: Plan defaults

The app starts in Plan mode. Read-only exploration and safe checks can run immediately, while file writes and write-like commands require switching to Act mode.

Chosen: one observable store

SessionManager is a plain service. AgentManager is the only UI-facing observable store, so React rendering has one subscription surface.

Chosen: projections over stored UI

The app stores facts as events, not rendered blocks. This lets display behavior evolve without migrating every old chat transcript.
