Data flow

From keystroke to restored transcript

A normal chat turn passes through input handling, command detection, session management, model streaming, event persistence, projection, and rendering. The data is intentionally transformed in narrow steps so each layer has one job.

Live events

While a run is active, `AgentRun` emits events into memory. `AgentManager` subscribes to the run and copies snapshots into `_liveEvents`, then projects them for rendering.

Persisted events

`RunOrchestrator` records non-start events through `RunRecorder`. `startRun` appends a `TURN_COMPLETE` checkpoint when the run promise resolves.

Plan/Act Tool Flow

The current mode lives in `AgentManager` state and is passed into `ChatService.startRun()`, `startRun()`, `createToolContext()`, and finally each tool factory. Plan mode allows read-only file tools and non-mutating command checks. It blocks `write`, `edit`, and write-like `runCommand` before filesystem mutation or shell execution. Act mode keeps confirmation, but `write` and `edit` attach a compact unified diff to the request. 

AgentManager mode
ChatService.startRun({ mode })
createToolContext({ mode, confirmBus, abortSignal })
tool executes:
  plan + mutation => blocked message
  act + write/edit => validate, diff, confirm, apply

Session Restore Flow

Switching sessions calls `AgentManager.switchSession(sessionId)`. The manager cancels the active run, updates `SessionManager`, clears persisted events temporarily, notifies the UI, loads checkpoint-safe events through `loadSessionEvents(sessionId)`, then notifies again. The UI never reads JSONL directly.

Normal restore intentionally uses completed events only. If a process dies after streaming partial output but before `TURN_COMPLETE`, `loadSessionEvents()` trims the incomplete tail. Raw event loading remains available for tests and debugging.
