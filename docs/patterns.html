Design Patterns & Decisions

The architectural patterns, design decisions, and trade-offs that shape Excelsior's codebase.

Patterns

1. Event Sourcing

The core architectural pattern. Every interaction between user, agent, and tools is recorded as an ordered sequence of typed AgentEvents. The event stream is the single source of truth.

agentStream.ts → AgentSession.emit() → AgentEvent[]
                                          │
                             ┌────────────┼────────────┐
                             ▼            ▼            ▼
                        SQLite DB    DisplayBlock[]  AI History
                        (persist)    (projection)    (memory)
PropertyBenefit
Immutable event logEnables time-travel debugging and replay
Dual projectionSame events → UI display + AI context history
Crash resilienceEvents persisted incrementally (sub-agent events survive crashes)

2. Pure Reducer for Projection

The event-to-display transform follows a reducer pattern for testability and incremental updates:

createProjectionState()            — initial state factory
reduceProjectionEvent(state, evt)  — reduce a single event into state (mutates)
flushProjectionState(state)        — finalize pending blocks → DisplayBlock[]

This design allows:

  • Processing events incrementally as they stream in
  • Resuming from a saved accumulator state
  • Unit testing the reducer with individual events
  • No need to re-process the entire event log on each render

3. Prioritized Keyboard System

Rather than relying on Ink's useInput callback order (which is unpredictable), the project built useKeymap() with a centralized registry and priority-based conflict resolution.

activeMaps: RegisteredMap[]
  │
  └── Each entry: { id, priority, enabled, timestamp, getMap }
        │
        ▼
  On keypress:
  ├── Parse combo via parseKeyCombo(input, key)
  ├── Check if local map has handler
  └── Sort activeMaps by (priority desc, timestamp desc)
      └── Execute only if THIS registration wins
PriorityHook
100useToolConfirmation — Y/A/N must work when prompt is open

4. Multi-Agent Fan-Out (Parallel Review)

The PR review system uses a "one orchestrator + N sub-agents" pattern rather than a single monolithic agent. Sub-agents run sequentially (due to tool call constraints) but each has a focused domain:

Orchestrator Agent
  ├── spawnSubAgent("Bug Hunter")          → logic errors
  ├── spawnSubAgent("Security Auditor")    → auth/crypto
  ├── spawnSubAgent("Code Style Reviewer") → style/consistency
  └── spawnSubAgent("Infrastructure Rev.") → CI/infra
        │
        ▼
  Collect all results →
  ├── Deduplicate
  ├── Rank by severity
  ├── Remove false positives
  └── Format as markdown

Each sub-agent runs as an independent ToolLoopAgent with its own AgentSession, enabling isolated event streams and crash containment.

5. Reactive Session Subscription

The AgentSession class implements the useSyncExternalStore contract that React expects:

class AgentSession {
  getSnapshot(): readonly AnyAgentEvent[]  — frozen event array
  subscribe(cb): () => void                — store listener registration
  // Internally:
  emit() → _events.push() → _snapshot = [..._events] → _notify()
}

This decouples the event system from React's rendering cycle. The session doesn't know about React; React subscribes to the session.

6. Write-Through Cache for CQRS

An in-memory LRU cache (max 10 sessions) sits between reads and writes to the SQLite database:

persistEvents(events)
  ├── SQLite INSERT (WAL mode)
  └── cacheEvents(sessionId, events)  ← write-through

loadSessionEvents(sessionId)
  ├── CACHE HIT → return cached events  ← zero DB reads
  └── CACHE MISS → SQLite SELECT → cache → return

This decouples UI reads from database writes, critical during high-frequency streaming updates.

Key Design Decisions

Decision: Event Sourcing over Direct State

All agent interactions are recorded as immutable ordered events. This provides full history replay, persistence, and decoupling at the cost of complexity in projection logic. Worth the trade-off for debugging and the "load older messages" feature.

Decision: Two Separate Agent Runtime Modes

The chat system and PR review system each have their own agent creation but share the same infrastructure. The chat agent runs in the main session; the review orchestrator runs as a separate session with dedicated tools. Sub-agents are nested sessions within either flow. This avoids a unified "supervisor" abstraction that would add complexity.

Decision: Static + Live Rendering Split

Frozen blocks (terminal status) use Ink's <Static> for zero re-render cost, while live blocks (still streaming) render normally. Blocks are frozen per-block (via isFrozen flag) rather than using a positional tail heuristic, avoiding the edge case where a fast tool call stays live longer than needed or a large output gets frozen prematurely.

Decision: Security-Conscious Tool Design

The runCommand tool blocks dangerous patterns (rm -rf /, mkfs, dd, shutdown), detects write operations, and requires user confirmation for any state-changing command. File write/edit tools also go through the confirmation bus. The grep tool skips node_modules, .git, dist, and files larger than 1MB.

Decision: API Retry with Exponential Backoff

The agent.stream() call is wrapped with retry logic (3 retries, 1s/2s/4s backoff) for transient errors (429 rate limits, 502/503/504 gateway errors, network connectivity issues ECONNRESET, ETIMEDOUT). The user sees a [Retry 2/3] message during retry rather than a fatal crash. After exhausting retries, the error surfaces with context.

Decision: SQLite WAL Mode for Concurrent Access

WAL (Write-Ahead Logging) enables concurrent reads while writing — essential since events are persisted asynchronously while the UI reads from the same database. The reader never blocks on the writer.

Decision: Nord-Inspired Theme

The UI uses a consistent Nord color palette with semantic color tokens (accent, success, error, text, muted) and glyph symbols, providing a polished, cohesive terminal aesthetic without external CSS dependencies.

Decision: Agent Instructions Over Fine-Tuning

The system prompt uses detailed behavioral instructions (tone scaling, response modes, tool usage rules) rather than a simpler prompt. This provides nuanced control over agent behavior at the cost of prompt tokens. The review orchestrator has its own dedicated system prompt for the multi-agent workflow.
