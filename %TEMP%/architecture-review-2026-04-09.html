Excelsior Architecture Review

April 2026 — focused on the @excelsior/agent-harness projection and event pipeline

1. TranscriptProjection is a God-class with 7+ responsibilities

Deepen by splitting projection context from lifecycle orchestration

Strong

Files

  • packages/agent-harness/src/projector/TranscriptProjection.ts (230 lines)
  • packages/agent-harness/src/projector/TurnStore.ts
  • packages/agent-harness/src/projector/LiveDrafts.ts
  • packages/agent-harness/src/projector/utils.ts
  • packages/agent-harness/src/projector/types.ts

Responsibilities

  1. Turn lifecycle (start/end/compact/fail)
  2. Assistant message streaming
  3. User message finalization
  4. Tool call lifecycle
  5. Sub-agent state tracking
  6. Task list management
  7. Display ID dedup across blocks
  8. AiHistory management (model-facing)
  9. Delegation to ProjectionHandlers

Problem

TranscriptProjection exposes four action namespaces (messages, tools, lifecycle, subAgents, tasks) but implements every action inline as closures over private state. This means every new event type requires adding a new method + a new namespace + new tests on the same class. The deletion test: if you delete TranscriptProjection, all five projection handlers would need to be rewritten. The complexity is concentrated — but it's concentrated into a single file with no seams between concerns. The apply() method at line 203 exists purely to satisfy the ProjectionContext interface but duplicates the Projector's own dispatch logic.

Solution

Split TranscriptProjection into a thin orchestrator that owns the turn list and delegates each domain to a focused sub-module:

  • TurnStore — already extracted, keeps turn list + current turn id
  • LiveDrafts — already extracted, keeps streaming drafts
  • BlockStore — new: owns the block display ID counter and materialization logic (extracted from LiveDrafts and TranscriptProjection)
  • SubAgentTracker — new: owns the subAgentStates map, extracted from TranscriptProjection
  • AiHistory — already extracted but accessed through TranscriptProjection; make it independent

The ProjectionContext interface should be split into MessageProjectionContext, ToolProjectionContext, etc. Each handler receives only the actions it needs — not the full context.

Before / After

// Before: 1 class, 5+ namespaces, 230 lines
class TranscriptProjection {
  private turns: TurnStore
  private history: AiHistory
  private subAgentStates: Map<string,...>
  private displayIdCounts: Map<string,number>
  private taskItems: ProjectedTask[]
  private drafts: LiveDrafts

  // 5 action namespaces as closures
  messages = { startAssistant, updateAssistant,
               finishUser, finishAssistant, ... }
  tools = { start, update, finish }
  lifecycle = { startTurn, endTurn, ... }
  subAgents = { apply }
  tasks = { replace }

  // Duplicated ID counting
  nextDisplayBlockId...
}
// After: 1 orchestrator + focused modules
class TranscriptProjection {
  private turns: TurnStore
  private drafts: LiveDrafts
  private blockIds: BlockIdCounter
  private subAgents: SubAgentTracker
  private taskItems: ProjectedTask[]

  // Handlers receive scoped refs
  // MessageHandler gets MessageScope
  // ToolHandler gets ToolScope
  // Both cannot access each other's state
}

Benefits

  • Locality: sub-agent logic lives in SubAgentTracker, not mixed with turn lifecycle
  • Testability: each focused module can be tested in isolation without constructing a TranscriptProjection
  • Interface depth: handlers receive exactly what they need, not the full context (less implicit coupling)
  • Deletion test: deleting SubAgentTracker removes sub-agent complexity entirely — it was shallow before

2. EventBus.emit() orchestrates 7 concerns in one method

Extract event construction, persistence, and notification into a pipeline

Strong

Files

  • packages/agent-harness/src/EventBus.ts (lines 73-135)
  • packages/agent-harness/src/EventStore.ts
  • packages/agent-harness/src/harness.ts (notify flow)

Steps in one method

  1. Check run finalization (guard)
  2. Resolve session from options or current
  3. Build causationId/correlationId chain
  4. Construct event via makeHarnessEvent
  5. Persist via EventStore.recordEvent
  6. Update session metadata
  7. Notify extensions
  8. Schedule UI snapshot update

Problem

The emit() method (line 73) is the central bottleneck of the harness event system. It mixes: (a) event construction (making the HarnessEvent object with causation tracking), (b) persistence (calling EventStore + sessionManager), (c) notification (extension hooks + UI listeners). These are three separable concerns with different change rates. Changing persistence format should not require touching event construction. The deletion test: deleting EventBus would require duplicating its logic in every caller. The depth is real, but the interface is shallow — every caller must understand the full pipeline.

Solution

Introduce an EventPipeline that separates construction from persistence from notification:

  • EventFactory — owns makeHarnessEvent + causation/correlation id chain
  • EventBus — thin: delegates to pipeline, keeps the createEmitter() convenience
  • EventStore — persistence only (already mostly there)
  • NotificationBus — new: owns extension hooks + UI notify scheduling

This changes the emit path from:

// Before
EventBus.emit(runId, type, data, options)
  → makeHarnessEvent(...) + eventStore.recordEvent()
    + sessionManager.sessions updated + extensions.emit() + notify()

// After
EventBus.emit(runId, type, data, options)
  → pipeline.process({ runId, type, data, options })
    → factory.create() → store.record() → notifier.broadcast()

Benefits

  • Seam: pipeline stages can be tested independently (test event construction without persistence)
  • Leverage: adding a new post-persist hook (e.g. metrics) adds one pipeline stage without touching emit()
  • Locality: causation tracking logic stays in EventFactory, not mixed with session metadata updates

3. ProjectionHandler receives full TranscriptProjection, not a scoped view

Scope the projection context per handler type

Worth exploring

Problem

The ProjectionHandler interface (in types.ts) passes the full ProjectionContext to every handler. MessageHandler.apply() receives projection: ProjectionContext which has messages, tools, lifecycle, subAgents, tasks — but it only uses projection.messages. Same for ToolHandler. The interface is vast relative to what any single handler needs.

Solution

Change ProjectionHandler's apply signature to accept a generic Scope parameter. Each handler declares its required scope type. The Projector maps the handler to the appropriate slice of the projection. 

// Before
interface ProjectionHandler {
  apply(event: AnyHarnessEvent, projection: ProjectionContext): void;
}

// After
interface ProjectionHandler<T extends keyof ProjectionContext> {
  apply(event: AnyHarnessEvent, scope: ProjectionContext[T]): void;
}

class MessageHandler implements ProjectionHandler<"messages"> {
  apply(event, scope: MessageProjectionActions) { ... }
}

Benefits

  • Interface depth: each handler's interface is exactly as wide as its needs
  • Locality: a bug in ToolHandler cannot accidentally mutate message state — it doesn't have access
  • Test surface: test a handler without constructing a full TranscriptProjection, just pass a mock scope

4. LiveDrafts duplicates display ID logic from TranscriptProjection

Both TranscriptProjection and LiveDrafts have their own nextDisplayBlockId

Worth exploring

Locations

  • TranscriptProjection.nextDisplayBlockId (line 224)
  • LiveDrafts.nextDisplayBlockId (line 153)
  • LiveDrafts.snapshotBlockId (line 159)

Shared concern

Both accept displayIdCounts: Map<string, number> via constructor. The counting strategy is identical but the methods are duplicated with slightly different edge-case handling (one uses append, the other checks against final blocks).

Solution

Extract a BlockIdCounter class that owns the map and provides nextId() and ensureUniqueId() methods. Both TranscriptProjection and LiveDrafts receive the same instance.

5. RunEventWriter and RunStepRecorder have blurry boundaries

Both manage overlapping tool input and message state

Speculative

Problem

RunEventWriter (131 lines) tracks tool inputs, buffers, started/completed sets, and emits events. RunStepRecorder (170 lines) also tracks tool calls, results, and messages, and delegates to RunEventWriter. The same callId appears in both classes' state. The RunEventWriter.endToolInput() and completeTool() methods accept a callId and look up toolName from internal state — but RunStepRecorder.recordToolCall() also tracks toolCalls in its own array. This duplication means a bug in one can silently diverge from the other.

Solution

Merge RunEventWriter into RunStepRecorder, or make RunEventWriter own all state and expose read-only queries. Currently RunStepRecorder.recordToolCall calls writer.endToolInput() and then separately stores its own toolCall copy. Instead, have RunStepRecorder query writer for the completed tool call data rather than duplicating it. 

// Before: duplicate state
// RunStepRecorder.toolCalls[] + RunEventWriter.toolInputs map
private recordToolCall(callId, toolName, input) {
  const toolArgs = this.writer.endToolInput(callId, input);
  this.toolCalls.push({ id: callId, function: { name, arguments: toolArgs } });
  // toolName also stored in writer.toolInputs
}

// After: single source of truth
// RunEventWriter owns all tool call state
// RunStepRecorder queries it:
private recordToolCall(callId, toolName, input) {
  this.writer.endToolInput(callId, input);
  // writer.getCompletedToolCall(callId) returns { name, args }
}

Benefits

  • Locality: tool call state lives in one place, not two
  • Leverage: fixing a tool lifecycle bug doesn't require editing two files

Top Recommendation: Split TranscriptProjection

Start with Candidate 1 (TranscriptProjection God-class). Here's why:

  • It blocks all three other candidates — scoping ProjectionHandler, extracting BlockIdCounter, and cleaning the LiveDrafts boundary all depend on TranscriptProjection being decomposed first.
  • It has the highest leverage: 9 responsibilities in 230 lines means every new event type or projection feature touches the same file and risks regressions in unrelated areas (e.g. a sub-agent change breaking tool display).
  • The deletion test passes: extracting SubAgentTracker, BlockIdCounter, and scoping ProjectionContext makes each module deeper — their interfaces shrink while their implementation stays the same size.
  • Test locality: currently every projection test constructs events and runs them through the full pipeline. After the split, you can unit-test SubAgentTracker.updateSubAgentState() directly — it's already a pure function in utils.ts but buried inside TranscriptProjection's closures.

After Candidate 1, do Candidate 2 (EventPipeline) — the EventBus bottleneck affects every emit, so deepening that seam pays off across all operations. Then Candidates 3, 4, and 5 are incremental improvements on the newly clean surfaces.
